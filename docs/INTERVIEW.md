# 面试口径

故意公开：让面试官提前看到这个项目的能力边界在哪，比现场被问出来好。

## 项目自述（100 字内）

一个单用户的小柜子：记录自己的衣服，按当天天气和场合给出三套搭配。
前端 React + Vite，后端 FastAPI + SQLite；推荐先走规则，可选接入任意 OpenAI
兼容模型，让模型只从候选里挑选，越界即校验失败并降级。

## 四个亮点

### 1. 多模型适配 + 无 key 降级

- **主张**：模型层是 OpenAI 兼容协议 + BYOK，`base_url` / `model` 可配，换供应商改两行配置；无 key、401、超时、限流、校验失败都退化成规则推荐，接口永远 200。
- **数字**：规则路径（天气已缓存）请求级 P50 约 2ms；模型路径实测 0.7–1.1s。
- **被追问时展开**：降级不是「catch 住返回空」，而是每条失败路径都有稳定短码（`no_key` / `timeout` / `rate_limited` / `invalid_ids` / `truncated` …），既进日志也进指标，前端据此显示「规则推荐 + 原因」。模型只替换三套里的第一套，后两套仍是规则结果。

### 2. 候选集约束 + 校验修复防幻觉

- **主张**：模型只输出 `item_id`，后端做四条硬校验（id 在候选池内 / 件数 3–6 / 不重复 / 品类覆盖：上装或裙装、下装或裙装、鞋，冷天要外套）；失败把「哪些 id 非法、缺了哪类」回灌重出一次，再失败降级。**防幻觉靠闭合校验，不靠 prompt。**
- **数字**：真实模型调用累计 13 次，出来的每一套都经过校验，未出现衣橱外单品；越界 id 在单测里被钉死（含「幻觉一次→修复成功」「幻觉两次→降级」）。
- **被追问时展开**：为什么不能只靠提示词——模型编造 id 是必然事件，提示词只是概率约束。候选池控制在 10–15 件，既压住幻觉面，也把 token 成本压到几百。

### 3. 成本与延迟可观测

- **主张**：每次 LLM 请求落一行指标，能查成功率、降级原因分布、缓存命中、token 消耗，以及**模型级**延迟分位（与请求级分开统计，避免被缓存命中的 2ms 拉低）。
- **数字**：`model_latency_ms` p50 763ms / p95 1078ms；单次约 prompt 365 / completion 47 tokens。
- **被追问时展开**：分位用 SQL `ORDER BY … OFFSET` 取，不把整表读进内存；`by_model` 只统计 `attempts > 0`，缓存命中和限流不计入模型用量；写指标失败只 warning，不影响响应。

### 4. 零 key 对外可跑

- **主张**：服务端不配 key 也能完整运行，访客自带 key 才能体验 AI；key 只存在访客浏览器、只走请求头，后端不落库不写日志（日志里只有 sha256 前 8 位指纹）。
- **数字**：限流 10 次/分钟/IP；推荐结果缓存 30 分钟；缓存命中不消耗限流额度。
- **被追问时展开**：限流超限**不返回 429**，而是 200 + 规则推荐 + `fallback_reason=rate_limited`，理由是页面不该因为后端限制挂掉；缓存与限流都是进程内实现，多 worker 不共享（这是明确的取舍，见「不要说」）。

## 不要说

- 不说「训练模型」——本项目没有训练，涉及图像时说的是「多模态预填 + 置信度弃答」。
- 不说「自研推荐算法」——说的是「工具调用循环 / 规则与模型分工」。
- 不夸大：缓存与限流是**进程内**的，多 worker 不共享；**无鉴权**，只适合本地或内网。
- 不承诺「零幻觉」——承诺的是「衣橱外单品不会被返回」，靠的是校验而不是模型自觉。

## 延伸

后面加的录入识别（品类/厚薄预填、购买截图提取）与对话入口，都是**围绕现有校验与降级链路**做的：识别结果同样要过闭合校验、置信度不够就弃答、没有 key 就静默退回手动；对话也只把「查天气 → 筛衣橱 → 组套 → 校验」这条链跑一遍，再让模型在候选池里选 id。

对话后来加了一点上下文（最近 6 条）和一句人味回复，但**没有改变「模型只提建议、约束在服务端」这个结构**：模型仍然只输出 `item_ids`，仍然要过同样的四条校验。

也就是说，这些功能没有改变核心主张——**模型只提出建议，真正的约束在服务端**；它们只是把同一条链路接到了更多入口上。
